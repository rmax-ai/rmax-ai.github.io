# Automatic Harness Synthesis: Turning Agent Failures Into Control Code

Workflow engines exist because process state needs explicit semantics. Policy-as-code systems exist because business rules and access rules need lifecycle management.
A harness can improve execution discipline. It should not become the source of business truth.
What AutoHarness actually shows
The AutoHarness paper studies the automatic synthesis of Python harnesses around LLM agents. Instead of only asking a model to produce better actions, the system searches over harness code. The harness can include functions such as propose_action(obs) and is_legal_action(obs, action). The loop rolls out the agent in environments, observes failed steps, consolidates failures, and asks an LLM to refine the harness code.
The important contribution is the target artifact.
AutoHarness is not just prompt optimization. It is not fine-tuning. It is not a hand-authored workflow graph. It is not a policy engine. It is not a verifier bolted onto the end of an agent.
It is a learned intermediate control layer.
The empirical results are narrow but meaningful. In structured TextArena game environments, the paper reports that learned harnesses can substantially improve legal-action rates and sometimes allow smaller models with a harness to outperform larger models without one. The exact numbers matter less than the architectural lesson: outer structure can be as important as raw model capability.
That claim fits a broader pattern in agent research.
ReAct showed that reasoning and tool use could be interleaved. Reflexion and Self-Refine showed that feedback loops can improve behavior without changing model weights. Code as Policies, Voyager, and Eureka showed that executable artifacts generated by models can carry useful behavior across steps or tasks. More recent scaffold and harness work, such as Meta-Harness and Harness-Bench, pushes the same point further: the model and the harness should be evaluated as a system configuration.
The useful conclusion is conditional, not universal.
Harnesses help most when the environment provides dense, machine-checkable feedback: invalid action flags, schema errors, exceptions, state-transition failures, policy denials, test failures, or explicit success conditions. They help less when the environment is ambiguous, delayed, adversarial, or normatively contested.
That is why automatic harness synthesis is more credible for structured enterprise workflows than for open-ended judgment.
Why enterprise workflows are a plausible next domain
Enterprise systems are full of structure.
Expense systems have request states, approval thresholds, receipt requirements, approver roles, reimbursement rules, and escalation paths.
Customer-support systems have ticket states, customer profiles, refund policies, priority levels, assignment queues, and escalation constraints.
Deployment systems have artifacts, environments, approvals, rollback hooks, health checks, logs, change windows, and release states.
These domains are not perfectly formal, but they are not free-form conversation either. They expose enough machine-checkable feedback to make harness synthesis plausible.
An agent that fails in these environments often fails in ways that are easy to classify:
The action schema is malformed.
The action is not valid in the current state.
A required field is missing.
The policy engine denies the action.
The target system returns a recoverable error.
The workflow cannot advance because a prerequisite is missing.
The agent retries the same invalid action.
The agent chooses the right tool but in the wrong order.
These are exactly the kinds of failures a deterministic harness can learn to reduce.
The harness does not need to understand the entire business. It needs to learn operational constraints around action validity, recovery, and execution order.
That makes the scope narrower and more useful.
A harness should not decide whether a refund is morally justified. It can learn that refund actions require a customer ID, ticket ID, eligibility check, and policy authorization.
Automatic Harness Synthesis: Turning Agent Failures Into Control Code
Enterprise agents do not only fail by saying the wrong thing. They fail by doing the wrong kind of thing at the wrong time.
They call tools with malformed arguments. They approve actions before the workflow is in the right state. They retry after a policy denial as if denial were a transient error. They skip required fields. They invoke irreversible operations without enough context. They confuse what looks operationally possible with what is actually authorized.
These are not only reasoning failures. They are control failures.
The standard response is to reach for larger models, longer prompts, more examples, or better tool descriptions. Those help, but they do not change the structure of the problem. A probabilistic model is still being asked to operate directly against a structured environment with schemas, state transitions, authorization rules, and side effects.
Automatic harness synthesis is a different lever.
The idea is simple: instead of relying only on the model to become better at every action, generate deterministic control code around the model. The model still proposes actions. The harness validates, filters, repairs, routes, retries, and sometimes compiles repeated behavior into executable logic. The environment provides feedback. Failures become counterexamples. Counterexamples drive harness revisions.
The result is not a smarter base model. It is a more disciplined system.
This matters because many enterprise failures are not mysterious. They are observable, structured, and repetitive. If an agent keeps submitting the wrong enum, calling actions out of order, missing required fields, or failing to recover after state conflicts, those failures can be converted into code.
The promise is not "self-improving agents" in the vague sense. The more precise claim is:
Repeated execution failures can be used to synthesize deterministic control layers around probabilistic agents.
That is the idea behind AutoHarness: Improving LLM Agents by Automatically Synthesizing a Code Harness, and it is the idea I am exploring in the open-source prototype Enterprise AutoHarness Lab.
The missing layer between agents and enterprise systems
A useful enterprise agent architecture has at least four layers:
Agent policy → Synthesized harness → Environment interfaces → Authoritative control plane
The agent is the stochastic proposer. Usually this is an LLM or an LLM-backed agent loop.
The harness is executable control code around the agent. It can normalize observations, validate actions, reject malformed outputs, repair invalid proposals, route tools, cache repeated decisions, or enforce retry discipline.
The environment interfaces expose the structured systems the agent interacts with: workflow APIs, ticketing tools, approval systems, deployment platforms, CRM records, data stores, and operational services.
The authoritative control plane owns the final decision. This includes policy engines, authorization systems, workflow engines, target-system permission checks, and transactional invariants.
The distinction is not cosmetic. It is the entire architecture.
A synthesized harness may learn that an expense cannot be approved before submission. It may learn that a deployment cannot start before artifact validation. It may learn that a support ticket should be escalated when refund eligibility is unclear.
But it must not become the final authority on whether a person is allowed to approve the expense, whether a refund is permitted, or whether a deployment should be released.
That authority belongs outside the harness.
This is where enterprise use differs from demos. In a toy agent environment, it is tempting to let the learned controller do everything. In an enterprise system, that collapses reliability, policy, and authority into the same generated artifact. That is the wrong direction.
Authorization systems such as Zanzibar, Cedar, and Open Policy Agent exist because authorization requires explicit, auditable, analyzable control.
A harness should not decide whether a deployment is strategically wise. It can learn that deployment cannot start before artifact validation and approval.
A harness should not decide whether an expense is legitimate. It can learn that approval attempts before submission are invalid and that missing receipt fields should be repaired or escalated.
This is the practical shape of the idea: use learned code for execution discipline, not for authority.
Enterprise AutoHarness Lab
Enterprise AutoHarness Lab is a proof-of-concept project built around one question:
Can an LLM automatically synthesize a code harness that reduces invalid agent actions, without becoming an ungoverned source of authority?
The project is intentionally small. It is not a production platform. It is a research lab for making the reliability question measurable.
The architecture separates five components:
Probabilistic Agent
Synthesized Harness
Authoritative Policy Engine
Workflow Environment
Evaluation System
The probabilistic agent proposes actions.
The synthesized harness predicts operational applicability.
The authoritative policy engine retains final authority.
The workflow environment executes state transitions.
The evaluation system records traces, counterexamples, metrics, and experiment results.
The key invariant is:
Harness acceptance never implies policy authorization.
Even if the harness accepts an action, the policy engine must still be called. Even if the harness predicts that the action is operationally valid, the target system or workflow engine must still enforce state and permission boundaries.
This is the difference between a reliability layer and an ungoverned policy layer.
The three prototype environments
The project uses three simulated enterprise workflows.
The first is expense approval. The environment includes actions such as submitting, approving, rejecting, and escalating expenses. The agent may fail by approving too early, missing receipt information, ignoring thresholds, or choosing the wrong escalation path. The harness can learn state-sensitive validity rules and repair common malformed actions. The policy engine still decides whether approval is authorized.
The second is customer-support tickets. The environment includes assignment, prioritization, resolution, refund handling, and specialist routing. The agent may fail by resolving unresolved tickets, issuing refunds without required checks, assigning to the wrong queue, or failing to escalate ambiguous cases. The harness can learn tool order, required fields, and common recovery paths. It must not become the source of refund policy.
The third is software deployment. The environment includes artifact validation, approval, start, cancel, rollback, and deployment-state transitions. The agent may fail by starting before approval, deploying invalid artifacts, retrying unsafe actions, or failing to roll back after a failed release. This is a strong fit because deployment systems often provide crisp feedback: command failures, state conflicts, missing approvals, health-check failures, and rollback signals.
These environments are deliberately simulated. That is a feature, not a weakness. Harness synthesis requires repeated failures, counterexamples, and controlled evaluation. Real enterprise systems are too risky as the first testing ground.
The core loop
The prototype follows a simple loop:
Agent proposes action
        ↓
Synthesized harness evaluates action
        ↓
Authoritative policy engine checks action
        ↓
Environment executes action
        ↓
Failure or success is recorded
        ↓
Failures become structured counterexamples
        ↓
LLM generates a revised harness
        ↓
New harness is evaluated on held-out scenarios
The loop is designed to answer one question at a time.
Does the harness reduce invalid actions?
Does it improve task completion?
Does it reduce repeated failures?
Does it recover better after errors?
Does it preserve policy authority?
Does it generalize to held-out scenarios?
Does it fail under schema or policy drift?
This framing matters because "the agent improved" is too vague. A serious evaluation needs to say which part of the system improved and under what condition.
What should be measured
A weak evaluation would only report task success.
That is not enough.
A harness can improve apparent safety by refusing too many actions. It can overfit to visible scenarios. It can hard-code accidental constraints. It can pass nominal tests while failing under schema changes. It can reduce invalid actions but block valid work. It can look clean because it is deterministic while still encoding the wrong invariant.

The most important pair is false acceptance and false rejection.
A permissive harness can look useful while letting bad actions through. A conservative harness can look safe while blocking valid work. Neither is enough.
A good harness improves execution validity without becoming a refusal machine.
The failure modes
Automatic harness synthesis has real risks.
The first is evaluator overfitting. This is well known from automated program repair. A generated patch can pass the available tests while still being wrong. The same applies to harnesses. A harness can satisfy the evaluator without capturing the intended invariant.
The second is specification gaming. If the evaluation rewards legal-looking actions too heavily, the harness may learn to maximize legality while ignoring task progress. If the evaluator has shortcuts, the synthesis loop may discover them.
The third is false confidence from deterministic code. Generated code feels more inspectable than generated text. But deterministic does not mean correct. A wrong rule written in Python is still a wrong rule.
The fourth is constraint fossilization. A temporary policy denial, schema quirk, or environment bug can become a durable rule in the harness. This is especially dangerous in enterprise systems where policies and schemas change.
The fifth is rule accretion. Repeated local repairs can produce a pile of exceptions that nobody understands. The harness becomes a sediment layer of past failures.
The sixth is authority leakage. This is the most serious architectural failure. If the harness starts deciding what is allowed instead of what is operationally applicable, it becomes an ungoverned policy engine.
The right response is not to avoid generated harnesses. The right response is to govern them like software artifacts.
Harnesses need a lifecycle
A synthesized harness should move through an explicit lifecycle:
GENERATED
→ STATICALLY_VALIDATED
→ SANDBOX_TESTED
→ EVALUATED
→ HUMAN_APPROVED
→ ACTIVE
→ MONITORED
→ RETIRED
Generated means the code was produced by the synthesis loop.
Statically validated means the code passes syntax checks, type checks, import restrictions, API contracts, and static safety rules.
Sandbox tested means the code runs in a restricted environment with no ambient credentials, no uncontrolled network access, time limits, memory limits, and explicit capability boundaries.
Evaluated means it has been tested against nominal, held-out, mutated, and adversarial scenarios.
Human approved means promotion depends on review, not only metric improvement.
Active means the harness is being used in the agent path.
Monitored means traces are checked for drift, false rejections, policy conflicts, and repeated failures.
Retired means stale harnesses are removed when schemas, workflows, or policies change.
This lifecycle borrows from software supply-chain and policy governance practices. Generated harness code should have provenance. It should be versioned. It should be reproducible. It should have rollback. It should not silently mutate in production.
The prototype keeps this simple: local execution, JSONL traces, file-system registry, deterministic tests, mock-first model clients, and an AST-based sandbox. Those are acceptable choices for a research kernel. They are not production security boundaries.
That distinction should stay explicit.
Why not just use larger models?
Larger models help. But they are not a control architecture.
A larger model may reduce some invalid actions, but it still produces actions probabilistically. It may still misunderstand schemas, skip state constraints, retry after denials, or fail under policy changes. It is also more expensive and harder to inspect.
A harness gives a different kind of leverage.
It can make invalid actions impossible or less likely before they reach the environment. It can repair common mistakes without another full reasoning pass. It can encode repeated operational patterns. It can reduce token usage. It can make part of the system inspectable as code.
The right comparison is not "harnesses versus better models." The right comparison is system-level:
Small model + no harness
Small model + manual harness
Small model + generated harness
Large model + no harness
If a smaller model with a generated harness outperforms a larger model without a harness on action validity, recovery, or cost, that is meaningful.
It does not mean the smaller model is smarter. It means the system is better structured.
Why not just write validators manually?
Manual validators are valuable when the rules are known.
But enterprise workflows have many implicit operational constraints. Some are obvious only after observing failures. Some are local to tools. Some live in undocumented conventions. Some appear only under state combinations. Some change when schemas evolve.
Manual validation also becomes an engineering bottleneck. Every new workflow requires someone to encode all known failure modes upfront.
Harness synthesis changes the workflow.
Start with a weak or partial harness.
Run the agent in simulated environments.
Collect failures.
Extract counterexamples.
Generate candidate harness revisions.
Evaluate against held-out and mutated scenarios.
Promote only when evidence improves.
This does not eliminate human engineering. It changes where human effort goes. Instead of hand-authoring every rule, engineers design environments, contracts, metrics, sandboxes, promotion gates, and review workflows.
The work moves from writing every guardrail to building the system that safely learns some guardrails from execution.
Where this approach fits
Automatic harness synthesis is a good fit for domains with four properties.
First, the environment must provide dense feedback. Schema errors, state failures, exceptions, policy denials, and test failures are useful. Vague human dissatisfaction is not enough.
Second, actions should be reversible or externally controlled. If an action has irreversible consequences, the harness should not be the final safeguard.
Third, the system must have explicit contracts. Tool schemas, action types, state models, and policy responses make failures learnable.
Fourth, evaluation must include drift and adversarial conditions.
A harness that works only on nominal scenarios is not enough.
This makes the approach suitable for:
Workflow-state validation
Schema-constrained APIs
Administrative operations
Support-ticket workflows
Expense workflows
Deployment pipelines
Cloud operations with rollback
Software test repair
Structured data transformation
Tool-use discipline
It is a poor fit for:
Authorization decisions themselves
Legal interpretation
Medical diagnosis
High-stakes financial decisions
Ambiguous compliance judgment
Interpersonal or political decisions
Any domain where feedback is delayed, contested, or impossible to formalize
The boundary is not whether the domain is important. The boundary is whether the environment can produce reliable feedback and whether final authority remains external.
The research roadmap
Enterprise AutoHarness Lab is organized as a staged research project.
The first milestone is a deterministic research kernel: common schemas, an expense-approval environment, a policy engine, a noisy agent, a manual harness, trace recording, evaluation, deterministic tests, and a CLI comparison path.
The second milestone is automatic synthesis: mock model client, initial harness generation, counterexample extraction, harness refinement, static validation, sandbox execution, candidate registry, and promotion logic.
The third milestone is complete evaluation: held-out test scenarios, generated harness comparisons, larger-model abstraction, metric suite, Markdown and HTML reports, CSV summaries, and code-diff reporting between harness versions.
The fourth milestone adds more environments: support tickets and software deployment.
The fifth milestone introduces drift experiments: schema mutations, policy mutations, resynthesis after mutation, recovery metrics, and before/after comparisons.
Post-v0.1 directions include candidate-tree search, Thompson-sampling-style refinement, OPA/Rego integration, real LLM provider adapters, dashboard visualization, parallel experiments, and a mutation catalog.
The roadmap matters because harness synthesis should not be judged from a single demo. It needs controlled experiments across environments, failure types, and drift conditions.
What this proof of concept can prove
A proof of concept can establish useful evidence.
It can show that generated harnesses reduce invalid action rates.
It can show that a harness improves recovery after failures.
It can show that a smaller model with a generated harness competes with or outperforms a larger model without one in structured workflows.
It can show that model-call count and token cost go down when repeated behavior is compiled into deterministic checks.
It can show that harnesses fail under schema or policy drift unless they are monitored and regenerated.
It can show that generated code needs review, sandboxing, and promotion gates.
That is already valuable.
What it cannot prove
It cannot prove production safety.
It cannot prove compliance correctness.
It cannot prove that the generated harness captured the real business invariant.
It cannot prove robustness against all adversarial users.
It cannot prove authorization correctness.
It cannot prove suitability for irreversible high-stakes actions.
It cannot replace policy-as-code, workflow engines, access-control systems, or target-system enforcement.
The credible claim is narrower:
In structured enterprise simulations, automatically synthesized harnesses can improve execution reliability while remaining subordinate to external authority.
That is enough.
Final synthesis
The next generation of enterprise agents will not be made reliable by model scale alone.
They will need scaffolds, validators, policy engines, workflow state, runtime monitors, sandboxes, evaluation harnesses, and generated control layers. Some of that code will be written by humans. Some of it can be synthesized from failures.
Automatic harness synthesis is one way to turn repeated agent failure into reusable system structure.
The model remains probabilistic. The harness becomes deterministic. The policy engine remains authoritative.
The workflow system remains the source of process truth. The evaluation system decides whether the generated artifact is better than what came before.
That is the architecture worth exploring.
Not agents that magically improve themselves.
Agents whose failures become code, whose code is evaluated, whose authority is limited, and whose deployment is governed.
That is a more realistic path to reliable enterprise agents.
